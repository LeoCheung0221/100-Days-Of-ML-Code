# 第 9 天 · 打乱日期

[第一阶段 · 模型](README.md) · 可运行

第 8 天改变的是进入正规方程的集合，斜率从 2.0500 变成 8.0500。本日不改变集合。五个配对原样保留，只打乱它们在表中的行序，再做一次批量 OLS。

系数与残差平方和不变。正规方程对配对求和，行序不是自变量。这证明估计不使用呈现顺序。这不证明横坐标里没有时间：时间就写在 `x_t` 里。

---

## 打乱的是行，不是配对

原顺序上的直线仍是

```text
ŷ = 3.2700x − 1.2900
RSS = 96.3390
```

固定的行序是 `[2, 4, 3, 0, 1]`，下标从 0 起，对应原来的第 3、5、4、1、2 行。这个顺序事先写死，不是按拟合结果挑的。每一行的 `(x, y)` 一起搬走。

再次 `lstsq`：

```text
ŷ = 3.2700x − 1.2900
RSS = 96.3390
Δβ₁ = 1.332e-15
ΔRSS = 1.421e-14
```

差别在机器精度里。平方损失的批量 OLS 是样本配对多重集的函数。交换求和顺序不改变和。因此任何行置换给出同一个 `β̂`，至多剩下舍入。

---

## 不变说明什么

它说明：把表从上到下读，还是按另一个顺序读，只要读到的还是那五对，估计就不变。第 8 天的窗口若按日历 `t` 选取，打乱行序同样不会改变窗口里的配对。按 `t` 求和的估计器都有这一个不变性。

它不说明三件容易混进去的事。

第一，`x` 不是被忽略的列。`x_t = t` 仍是设计矩阵的第一列。打乱行序没有把日期从配对里拿掉。

第二，这不是「成绩对时间不敏感」的许可证。若把收盘重新分配到另一个日期上，配对就断了，`RSS` 一般会变。那是另一个实验。本日的脚本不拆配对，所以也不报告那个变了的数。

第三，一个按到达顺序更新的递归估计没有这个不变性。本日的估计不是递归的。它把五行一次读完。顺序只存在于文件里，不存在于目标函数里。

所以「不识时间」这句话本日收紧成一句可以核对的话：批量平方损失不识行序。日历坐标仍然在模型里。

## 复现

```bash
python days/09-row-order/row_order.py
```

脚本应打印两次 `y = 3.2700 x + -1.2900`、两次 `RSS = 96.3390`，以及 `1e-14` 量级的 `delta RSS`。实现是 [`row_order.py`](../../days/09-row-order/row_order.py)。

## 本日的边界

不变的是水平残差的平方和。下一日在同一条直线上另报一个泛函：收盘的一日变动方向。价格残差小，方向仍可以错。两个分数都要交。行序不变性不会替方向分数作答。
